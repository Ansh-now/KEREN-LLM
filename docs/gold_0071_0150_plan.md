# KEREN Gold 0071-0150 Plan

Goal: reach 150 manually designed Gold records without padding the dataset with shallow paraphrases.

## Owner-context policy
KEREN should learn how to USE owner context, not memorize private biography.

Allowed stable context in examples:
- owner builds KEREN and engineering/automation projects such as DodlAx and WakeWear
- KEREN is intended as distributed execution/control infrastructure across software and devices
- owner commonly communicates in concise Roman-Hindi/Hinglish with abbreviations and follow-up questions
- owner often asks concept-first questions, tests an explanation with a counterexample, reports concrete symptoms when debugging, and prefers practical stepwise answers
- technical interests relevant to KEREN: Python/FastAPI, Git/GitHub, Flutter/Dart, Kotlin/Android, C/C++/Arduino/ESP32, Windows/Android control, browser automation, electronics, planning, verification, recovery and safety

Never bake into Gold records: passwords, credentials, exact address, DOB, IDs/account numbers, private contacts, raw financial/account data, or other unnecessary sensitive personal data.

Owner facts that can change belong in memory/profile context. The model is trained to retrieve/use that context rather than hard-code it into weights.

## 80-record allocation
- 0071-0080: owner context + conversational dynamics (curiosity, counters, corrections, incomplete assumptions)
- 0081-0090: Windows fundamentals (processes, services, files, PATH, environment variables, Control Panel/Settings, Device Manager, Task Manager, permissions)
- 0091-0100: macOS fundamentals (Finder, apps, processes, System Settings, permissions, Terminal, launch/open behavior, paths)
- 0101-0110: Git/GitHub fundamentals and recovery (status, add, commit, branch, merge, pull, push, conflicts, reset/revert distinctions, large-file mistakes)
- 0111-0120: Flutter + Dart (widgets/state, async, navigation, build/debug, packages, platform issues)
- 0121-0130: Kotlin + Android (Compose, lifecycle/state, permissions, services, intents, accessibility/BLE patterns)
- 0131-0140: Python/FastAPI + system/network reasoning (APIs, WebSocket, concurrency, validation, persistence, HTTP/local networking)
- 0141-0150: integrated KEREN hard cases combining owner context, cross-device execution, coding, OS knowledge, ambiguity, safety, verification and recovery

## Gold quality rules
1. Every record teaches a distinct decision boundary, concept, failure mode, or execution behavior.
2. No fake execution or fake verification.
3. Current/live facts require a current-data tool; static fundamentals do not.
4. Commands are distinguished from questions and explanations.
5. Ambiguity is resolved only when it materially affects execution.
6. Consequential actions preserve confirmation/authority boundaries.
7. Tool output and verification evidence override assumptions and stale memory.
8. Recovery is bounded; retries do not loop forever.
9. User corrections update the working context; they do not silently retrain weights.
10. Hinglish/STT variants remain natural rather than artificially misspelled everywhere.
11. Counterexamples should test the premise instead of making KEREN agree automatically.
12. Coding examples should teach root cause + correct patch direction + verification, not only syntax.
13. OS examples must preserve Windows/macOS distinctions instead of pretending commands/settings are interchangeable.
14. Owner-specific examples must be useful even if mutable owner facts are supplied through memory at runtime.
15. 150 is a quality milestone, not a stopping point; validation and coverage audit follow before training promotion.
